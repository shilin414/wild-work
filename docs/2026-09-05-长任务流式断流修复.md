# 长任务流式断流修复（workbuddy / qoder 在 120 秒被硬切断）

日期：2026-09-05（排查 + 修复）
涉及：`wild-work` 源码、`bin/config.json`、可执行文件

---

## 1. 结论先行

**根因是 Go 的 `http.Client.Timeout` 会掐断 SSE 长流。**

traework 的 `ChatStream` 走独立的 `StreamHTTP`（未设 Timeout），所以长任务一直没事；
workbuddy 和 qoder 复用带 Timeout 的 `HTTP`，单次流式请求一旦超过 120 秒就被硬性切断，
表现为「执行任务执行一会就停下来」。

| 渠道 | 修复前 ChatStream 用的 client | 有效超时 | 修复后 |
|---|---|---|---|
| traework | `StreamHTTP`（无 Timeout） | 无限 | 不变（基线） |
| workbuddy | `HTTP`（Timeout 120s） | 120s | 改用 `StreamHTTP`（无限） |
| qoder | `HTTP`（默认 180s，被配置覆盖为 120s） | 120s | 改用 `StreamHTTP`（无限） |

修复后实测：qoder 从 120.002s 硬断变为 **143.98s 正常完成**，
workbuddy 长任务 **273.77s（4.5 分钟）正常完成**。

---

## 2. 问题现象

1. 用 traework 渠道跑长任务一直顺畅；换 workbuddy 或 qoder 渠道，任务跑到一半就停。
2. 客户端拿到的是半截流，没有 `data: [DONE]` 收尾，直接判定失败。
3. `bin/data/app.log` 里**找不到任何相关错误**——断流是完全静默的。

---

## 3. 根因分析

### 3.1 Go `http.Client.Timeout` 覆盖「读完响应体」的全过程

官方文档对 `Client.Timeout` 的定义包含连接、重定向与**读取响应体**。
对 SSE 流式响应来说，只要这一轮生成没结束，body 就一直在读；
超过 Timeout 后读取返回：

```
context deadline exceeded (Client.Timeout exceeded while reading body)
```

于是长输出（大量代码生成、长思考链、连续工具调用）必然被切断。

### 3.2 三渠道客户端不一致（关键代码）

| 位置 | 说明 |
|---|---|
| `internal/traework/client.go` `New()` | 单独建 `StreamHTTP: &http.Client{Transport: tr}`（**无 Timeout**） |
| `internal/traework/client.go` `ChatStream()` | `hc = c.StreamHTTP`（非 nil 时优先） |
| `internal/upstream/client.go` `New()` | 只有 `HTTP: &http.Client{Timeout: 120s, ...}` |
| `internal/upstream/client.go` `ChatStream()` | 直接用 `c.HTTP` |
| `internal/qoder/client.go` `NewWithTimeout()` | 只有 `HTTP: &http.Client{Timeout: timeout, ...}`（默认 180s） |
| `cmd/wild-work/main.go` | 三渠道 `HTTP.Timeout` 都被 `cfg.Upstream.TimeoutSeconds` 覆盖，**但 traework 的 `StreamHTTP` 没被覆盖** |

所以无论 `config.json` 怎么调，对 trae 的流式毫无影响，
对 workbuddy / qoder 则是硬杠杆。

### 3.3 两个放大因素（让问题几乎无法自查）

1. **断流静默**：`internal/server/handler.go` 原来是
   ```go
   _ = rt.Upstream.Stream(w, rc)
   ```
   错误被丢弃 → 不记日志、不 `NoteError`、不 `stickyClear`、不轮转账号、不重试。
2. **不补 `[DONE]`**：`internal/upstream/sse.go` 与 `internal/qoder/sse.go`
   在读到非 EOF 错误时直接 return，不写收尾的 `data: [DONE]`，
   客户端收到半截流只能判定失败。

## 4. 排查过程

### 4.1 对照实验 + 精确计时（决定性证据）

用同一 prompt（数 1→3000，max_tokens=30000，stream=true）分别请求：

| 渠道 | 结果 | 耗时 |
|---|---|---|
| qoder/qwen3.8-max | HTTP 200，**流被截断** | **120.002588s** |
| traework/DeepSeek-V4-Pro | HTTP 200，正常跑完 | 136.853381s |

`120.002588` 误差仅 2.6 毫秒，精确等于 `Client.Timeout=120s`——
这个数字一出现就能排除网络抖动，直接锁定超时硬截断。

### 4.2 支线：qoder 的 `transport error: EOF`

排查中发现日志里有 24 条 qoder EOF，单独核查结论如下：

| 日期 | 次数 | model key | 错误 |
|---|---|---|---|
| 08/27 | 1 | `qmodel_38max` | 504 `<html>` |
| 08/30 17:42–17:55 | 24 | `gfmodel` | transport EOF |
| 08/31 | 3 | `gmodel` | 504 `<html>` |
| **09 月至今** | **0** | — | — |

`gfmodel` 不在静态表（`internal/qoder/constants.go` `staticModelKeys`）里，
它来自上游动态模型接口，即 **`glm-5.3-flash`**（`glm-5.3→gmodel` 的 flash 版本）。
当时该模型刚出现在模型列表、chat 网关尚未就绪，握手后直接断连。

**结论：历史问题，已自愈，无需处理。**
实测 `qoder/glm-5.3-flash`、`qoder/glm-5.3`、`qoder/qwen3.8-max` 现均返回 200。

## 5. 变更清单

### 5.1 `internal/upstream/client.go`（workbuddy）— 新增无超时流式客户端

```go
// StreamHTTP 专供 SSE 流式请求（/v2/chat/completions）。
// 不设 Timeout：Go 的 http.Client.Timeout 覆盖「连接 + 重定向 + 读完响应体」，
// 会硬性掐断持续输出的长流（长任务 120s 即断）。与 traework 的 StreamHTTP 对齐。
StreamHTTP *http.Client
```

`New()` 中 `StreamHTTP: &http.Client{Transport: tr}`（复用同一连接池，不设 Timeout）；
新增 `streamClient()`；`ChatStream()` 改用 `c.streamClient().Do(req)`。

### 5.2 `internal/qoder/client.go`（qoder）— 同样处理

`NewWithTimeout()` 中新增 `StreamHTTP: &http.Client{Transport: tr}`；
新增 `streamClient()`；`ChatStream()` 改用它。

### 5.3 `internal/server/handler.go` — 断流不再静默

```go
if serr := rt.Upstream.Stream(w, rc); serr != nil {
    log.Printf("stream aborted platform=%s uid=%s model=%s elapsed=%s err=%v",
        rt.Kind, acct.UID, model, time.Since(reqStart).Truncate(time.Millisecond), serr)
    rt.Pool.NoteError(acct.UID, h.cfg.ErrThreshold, h.cfg.ErrCooldown)
    h.stickyClear(rt)
}
```

响应头已发出无法改状态码，但错误必须记录并计入账号健康度，下次自动换号。
非流式的 `Aggregate` 出错路径同样补齐日志与冷却（原来也是静默的）。

### 5.4 SSE 异常收尾补发 `[DONE]`

`internal/upstream/sse.go`、`internal/qoder/sse.go`、`internal/traework/solosse.go`
三处统一：读异常（非 EOF）时先补发 `data: [DONE]` 再返回错误，
让客户端能正常收尾而不是一直等待或直接失败。

### 5.5 `cmd/wild-work/main.go` — 加注释说明

明确 `timeout_seconds` 只覆盖非流式客户端，三个渠道的 SSE 流式请求各走独立的
`StreamHTTP`（不设 Timeout）。

### 5.6 `internal/app/app.go` — 版本号 2.0.1 → 2.0.2

### 5.7 `bin/config.json` — `timeout_seconds` 120 → 900

兜底措施。注意该值同时作用于 `FetchModels` / `FetchModelPricing`，
不宜设得过大（不建议 3600）；账单/签到接口走独立的 30s 客户端不受影响。

## 8. 遗留与提醒

1. **`timeout_seconds=900` 的副作用**：该值同时作用于模型列表与定价拉取。
   若上游接口卡死，最坏要等 15 分钟才超时。当前三渠道拉取均正常（约 0.2s），
   如后续发现模型列表刷新变慢，可调回 300 左右——流式请求已不受此值影响。
2. **沙箱内 curl 的坑**：Git Bash 沙箱里 `curl -o <path>` 会静默失败导致客户端
   立即断开（表现为 0.35s 返回 0 字节，服务端报 `write tcp ... wsasend`）。
   测试一律用 shell 重定向 `> file` 而非 curl 的 `-o`。
3. **再看断流时怎么查**：直接搜 `app.log` 里的 `stream aborted` / `aggregate failed`，
   日志带平台、账号、模型、耗时与原因，可立即定位是哪个账号、跑了多久。
4. **qoder `gfmodel` EOF 已自愈**，无需处理；若再出现同类「某模型连不上但模型列表里存在」，
   先确认是不是上游新模型未就绪。
5. **systray 图标告警**（`unable to load icon from temp file`）属既有问题，
   只影响托盘图标显示，HTTP API 正常。
